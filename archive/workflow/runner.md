# NPVE runner: operator and executor guide

This is a small set of reusable NPVE programs, layered on the existing record store and version-3 workflow. It does not authenticate, pick a model, change risk, approve designs, inspect pixels, or start a batch. No live Figma execution was used to validate this implementation. The completed Patient Summary body at commit `50c680e` is a historical example, never a replay target.

## Fresh task

1. Read AGENTS.md and CLAUDE.md; run `node scripts/workflow/validate-workflow.js`. Generate the selected packet with `node scripts/workflow/npve-runner.js handoff <item-id> <new-evidence-folder>`. Read its `handoff.json`. It contains the selected record, exact approval evidence, dependencies, appearance specification, checkpoint and controls; since version 2 (2026-09-12) the canonical rules, the NPVE rules, the selected active findings and CLAUDE.md are referenced by path and digest under `references` and read from those files, never copied. Run `verify-handoff <path>` on resume; stale packets must be regenerated. If a proposed item has no record, use normal lean startup and the record gate first. The packet is a projection, never authority or permission.
2. Inspect actual authenticated tools in the current client and their documentation/skills. Make sequential read-only calls with explicit file keys against source, target, and required published components. Verify the complete page inventory, node name/type/parent, dimensions, component key and exact owning-set definitions. When a read-only source set refuses its definitions (`componentPropertyDefinitions` throws), the read program quotes the exact error and reads the set's identity, page, geometry and every variant's name and `variantProperties` instead; the plan's source node carries that record as `definitionsUnreadable`, and the control is marked `definitions: "unreadable at source"` with a flag naming the set (`scripts/workflow/source-definitions.js`, record workflow_flowsheetsResume_2026-09-12). Target and library components are never accepted that way. Save full readbacks; never treat the historical IDs in the packet as fresh proof. New library imports must be imported and used in the same guarded call; these utilities intentionally use already-local components. Do not write the source, library or deprecated kit.
3. Reuse a reviewed appearance specification. The model checks source copy, visibility, hierarchy, supported properties and tokens against code/Storybook and the recorded scope. Record any factual correction. New design decisions, missing tokens, ambiguous hierarchy, identity disagreement, invented content, truncated results or rasterized rebuilt UI stop execution. Frozen source reference images are the sole image exception.
4. Use the existing apply script / `openRecord`, regenerate the contract, populate `execution.json` from fresh evidence, and use `start-batch.js` normally. Runs remain version 3, checkpoints remain version 1/2. Only the operator/planner changes risk; use their exact per-item quote where required. Do not copy the Patient Summary quote to a new item. Declare every required visible state and final comparison milestone in order.
5. Prepare a small JSON plan for the next step using the operations below. A model reviews this configuration, not regenerated program text. Bind `repositoryRunner(adapter, itemId)` to the existing authenticated tools and call `await runner.step(plan)`. Reads run sequentially; the target is reverified inside the mutation script. `check-batch` runs immediately before the mutation. All calls, including image creation, name the target explicitly. A runner receipt contains only identities, counts, differences and the full evidence path/hash.
6. Export a PNG of that live state, save it, **inspect it**, show the operator as required, and update the existing checkpoint with actual node IDs, observations and the render. The runner never marks a milestone verified. A later milestone cannot run until every earlier milestone is verified. Do not mark a finished state pending merely to replay it. Preferred-menu steps belong after the required state reviews. Keep the dedicated Reference / Rebuild / Change log helpers and comparison per required state.
7. Collect the full-page and instance audit with `runner/audit.js`'s read-only script, save its complete result and use `audit()` for deterministic differences. Supply baseline/final shared snapshots with dimensions, variants and full definitions, and the explicit expected additions. Root COMPONENT/INSTANCE types and expected root swap references are excluded from paint/descendant-reference comparisons. This does not exclude descendant paint or property-reference failures. Inspect every required state and final whole-form comparison; populate appearance review and all ten standing checks from actual evidence, including checks requiring judgment.
8. Record and perform any proof archiving through a guarded authorized step before finalization; retain IDs and README. Use `runner/closeout.js` from the batch's finalize script: `closeout(itemId, finalBody)` checks readiness without finalizing; `closeout(itemId, finalBody, {dryRun:false})` runs the existing guard, finalizes through `finalizeRecord`, regenerates the contract and runs `finish-batch`. `finalBody` must contain actual standing-rule results, report/screenshot citations, proof disposition and a repository-relative `operatorPresentationEvidence` note. It creates no approvals or visual passes. If finish fails after DONE, fix evidence/tooling and rerun finish; never edit the DONE record. Commit the bounded diff with generated files, then use the established milestone-tag policy.

`runner/evidence.js` provides `evidenceDraft(item, auditResult, fileIdentity, readbackPaths)` and `reportDraft(item, details)` for reusable closeout scaffolding. Drafts deliberately leave visual inspection and behavioral property verification incomplete. A matching reference count cannot prove that a property actually changes rendered content.

## Tool adapter

The runner accepts two async functions. Neither may use cached replies, retry writes, batch calls concurrently, log credentials or return truncated data. This is a transport interface, not an alternate authorization system.

```js
const {repositoryRunner} = require('./scripts/workflow/runner/core');
const runner = repositoryRunner({
  async read({fileKey, code}) {
    // Call the current client's authenticated Plugin API tool with exactly this
    // explicit fileKey and code. Unwrap the complete JSON return value.
    return await authenticatedPluginCall({fileKey, code});
  },
  async mutate({fileKey, code}) {
    return await authenticatedPluginCall({fileKey, code});
  }
}, selectedItemId);
const summary = await runner.step(plan);
```

`authenticatedPluginCall` above is the client-owned bridge, not an installed function. Resolve the actual tool name, schema and JSON envelope from current tool discovery. A client able to call tools only from its orchestration runtime should load this module into that runtime or expose the two callbacks through a local bridge. Do not paste a compiled mutation directly into a tool to skip the guard. The CLI's `compile` command only produces inspectable code; it never executes it. No provider SDK, server, credentials or endpoint is included. Use one runner instance and await each call; the host must serialize other Figma work too. These programs are not a sandbox against a dishonest adapter or executor.

For clients without an in-process callback bridge, the included file-backed bridge works with ordinary command tools: add the selected `itemId` to the plan and run `node scripts/workflow/npve-runner.js execute <plan.json>` in a persistent terminal with stdin. It emits one small `tebra.npve-tool-request` at a time. Read `requestFile` programmatically, pass its explicit file key and code to the discovered authenticated tool, unwrap and save the complete JSON reply, then send `{"sequence":1,"replyFile":"<repo-relative-file>"}` to the waiting terminal. Do not print the full request/reply into model context. A mutation request includes `immediatelyBeforeDispatch`: run that exact check-batch command again immediately before dispatch, because a terminal/tool handoff can delay the runner's own guard. Stop if it fails; never dispatch a queued stale request. This uses existing tool authentication and introduces no service or endpoint. The bridge is opt-in and never used by dry runs.

The adapter returns native JSON, with `complete:true`, echoed nonce and exact identities for reads. It must detect tool errors/truncation before unwrapping. Results are saved under `<batch>/runner/<step-id>/`. An immutable intent marker precedes each attempt. Replay of that step is refused, including after process loss. A failed/uncertain mutation also adds an unresolved entry to `execution.json`. Read affected nodes and parent children once to classify applied/not applied/uncertain; resolve only with evidence and a different supported approach. Two unsuccessful attempts stop that operation; renaming a step or changing model does not reset the policy. The runner does not automatically retry or certify that a renamed operation is different.

## Configuration reference

Every plan has `id` (unique lowercase slug), `fileKey` (NPVE target), `milestone` (pending checkpoint name), `requiresVisual` (additional reviewed prerequisites), `appearanceEvidence` (saved reviewed specification/configuration), `reads`, and `operation`. Each read has `fileKey`, exact `pages` strings (`id name`) and `nodes`. Every expected node has `id`, `name`, `type`, `parentId`, and geometry where applicable; every component also has `key` and full native `definitions` from the owning set, or, on a source read only, `definitionsUnreadable` (the exact error, the set's identity, page and geometry, every variant's name and `variantProperties`) for a read-only set Figma cannot read. Fresh reads verify these immediately, and target checks repeat in the mutation call. Geometry/default drift stops before mutation.

Supported operations deliberately cover established patterns only:

| kind | Required operation fields | Behavior |
|---|---|---|
| `shell` | `parent`, `shell`, `properties`, `bodyProperty`, `bodyLayer`, `blocks:[{component,properties}]`, `bodyName`, `helperName`, `width:550`, `bodyWidth:518`, `spacing:{key,name,value:16}`, `x`, `y`, `helperX` | Creates a transparent live body and sheet helper; swaps into the existing shell; only placed instances hug content. |
| `helpers` | `parent`, `row`, `rows` (exact exposed row properties), `referenceName`, `changeName`, `imageName`, `width`, `height`, `logWidth`, `x`, `y`, `logX`, `paper:{key,name,valuesByMode}`, `spacing:{key,name}` | Creates dedicated source rectangle and live Change log/Row helper, bound paper surface and 16px insets. Supply exact source caption and reviewed change text; no generated content. |
| `comparison` | `parent`, `master`, `name`, `properties`, `x`, `y`, `slots:[{role,column,name,property,helper}]` | Exactly three distinct Reference/Rebuild/Change log component helpers; exact unique layer paths; 1:1 sizing and clipping off on placed slots. |
| `preferred` | `master`, `additions:{exactProperty:[{id,key,type}]}` | Verifies each addition; deduplicates and appends; preserves all definitions/defaults/geometry. |
| `reference-image` | `rectangle`, `referenceName`, `source:{fileKey,nodeId,scale:2,exportedAt}`, `png` (byte array) | Guarded image creation and fill of an empty reference rectangle; checks PNG dimensions against 2x source size. Never paints rebuilt UI. |

Supply `fonts:[{family,style}]` on the plan for all text touched. Programs await them. Children are appended immediately; no detached instances, deletes, arbitrary callbacks, library edits, shared geometry changes or automatic clone/variant conversions are supported. For an unsupported operation, keep the established recorded and guarded workflow instead of stretching this runner. No extra design batch is authorized by the tooling.

## Measurement and validation

`npve-runner.js usage observations.json` consumes normalized per-response rows: `{kind:"response",runId,responseId,source,cachedInput,uncachedInput,output}`. Every token field is a measured nonnegative integer or `null`. The transport normalizer must explicitly document whether its provider reports cached input inside total input; subtract it only when both counters and that definition are available. Reasoning output is a subset, not extra output. Cumulative counters and conflicting duplicates are rejected; identical response IDs within a run are counted once. Missing observations yield null totals plus clearly named observed subtotals. Credits/prices stay null; record separately sourced operator cost observations through the existing metrics convention. Never infer conversions. Mark prefix versus complete-run coverage in the source evidence.

The generated context measurement compares **identical required information**, pretty versus compact JSON, with equal parsed digests. It also reports the broader source-file size separately. It measures bytes, not tokens or credits. Since packet version 2 the compact packet must stay under the `runnerPacket` ceiling in `workflow/check-catalog.json` → byteCeilings; generation fails above it. Reused programs and compact receipts are expected to reduce script generation and model-facing readback volume, but live tool/response/credit savings have not been measured. The initial existing context command measured 1,564,702 legacy bytes and 157,420 lean bytes (89.9%); that is a different baseline and must not be combined with this comparison.

Run `node scripts/workflow/runner-self-test.js` for the representative offline three-state prerequisite / guarded preferred-update dry run and meaningful failure fixtures, and `node scripts/workflow/runner-plugin-self-test.js` for shell/helper/comparison structural tests. Mock approvals, reviews and a 1px PNG exist only in a temporary fixture directory. Real Patient Summary shared property and all-page unbound-paint snapshots are checked without modifying the historical folder. Also run existing workflow, execution, identity and schema self-tests. No test calls Figma.
